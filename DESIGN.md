# dotunnel design

`dotunnel` is a self-hosted stdio MCP server for one configured working directory and administrator-defined fixed tasks, plus operator-only helpers that connect it to a private Secure MCP Tunnel. It runs on the user's own Linux host. It is not a hosted service, a public HTTP endpoint or a sandbox for arbitrary code. MCP is the protocol the Tunnel carries, so the server is the core; the name only drops it from the product/command name.

## Runtime and architecture

Linux, Python >=3.11, official MCP Python SDK 2.2.x. No tmux or terminal-multiplexer dependency.

One distribution (`dotunnel`), one import package (`dotunnel`) and one console command (`dotunnel`; `python -m dotunnel` is equivalent). Operator subcommands are `help`, `setup`, `update` and `doctor`; engine subcommands are `serve` (stdio MCP), `cli-job` and `claude-token`. Setup-generated Tunnel profiles run `python -I -m dotunnel serve --config ...` with the installing interpreter, excluding cwd and ambient Python paths from module discovery; managed native tasks use the absolute `dotunnel` launcher with `cli-job`. Updating the package does not rewrite an existing profile; operators must add `-I` to pre-0.1.3 module commands before restarting.

`dotunnel serve --config /absolute/trusted/config.json` loads configuration before opening stdio. The configured root must exist, be a non-symlink directory, and not be `/` or the executing user's home directory. Configuration is outside the writable root, a regular non-symlink file, owned by the executing user, and not group/world-writable. There is no default root, task discovery or ambient credential read. Unknown configuration fields are rejected.

Tools:

- `list_files(path=".")`: bounded immediate entries, no symlink traversal or dot/credential files.
- `read_file(path)`: bounded UTF-8 regular file with its SHA-256.
- `search_files(query, path=".")`: bounded literal content search, never regex or shell; skips inaccessible/protected/non-text files and reports traversal truncation.
- `write_file(path, content, expected_sha256=null)`: null creates a new file only; a hash explicitly permits replacement of an unchanged existing file. Existing directories required. No delete/move/chmod tools.
- `list_tasks()`: named administrator-defined task descriptions, not ambient commands/environment.
- `run_task(name)`: start one exact trusted argv/cwd, with no caller args/env/destination. Return immediately after successful spawn with a stable `result_id`, `status: running`, `exit_code: null`, empty `output` and `truncated: false`; do not wait for completion.
- `get_task_result(result_id)`: retrieve a snapshot of that running or terminal result from the current process's bounded in-memory cache. Querying never starts or retries work.

Read tools carry read-only annotations; `write_file` and `run_task` are explicitly mutating. Tool hints are not authorization. Arguments not in a tool's signature are refused before dispatch, so a rejected customization cannot start a task.

## File boundary

All client paths are relative, reject `..`, absolute paths, NUL and protected components. Hidden files/directories, common credential/key files and the MCP config are not exposed. Linux directory-fd operations with O_NOFOLLOW reject symlink traversal, and regular file checks reject devices/FIFOs/sockets and multiply-linked files. Read/write limits 64 KiB/file; listings <=200 rows; search <=100 matches, <=1000 visited entries and <=4 MiB scanned. Returned output is bounded. No raw exception with host paths or file contents is sent to clients.

These checks limit file tools, NOT arbitrary code run by tasks. Administrator-defined tasks and executables must be trusted. Running builds/tests or editable scripts can execute code with the runtime user's complete OS permissions. A working directory, fixed argv or a different username is NOT a sandbox. Task definitions and runtime code must stay outside the remotely writable root. Credential-shaped paths are blocked, but arbitrary secret text in allowed files or command output cannot be guaranteed absent.

## Task boundary

Only configuration-defined names resolve. Absolute argv[0], exact argv, explicit root-relative cwd, no caller-provided arguments. Local config validates unknown fields, types and finite bounds. Each task has a positive timeout <=300 seconds (default 60). One active task; overlapping requests fail busy before spawn. Combined captured stdout/stderr <=16 KiB; drain excess without accumulating it, include truncation. No inherited OpenAI/SSH/cloud credentials; child env is a small fixed set including PATH and HOME rooted at the workspace. stdin is closed. Results have the same six fields (`result_id`, `task`, `status`, `exit_code`, `output`, `truncated`); a running snapshot has no partial output. Final states are `completed`, `timed_out`, `failed` or `cancelled`. `completed` does not mean exit code zero. Post-start failures become retrievable terminal results, not unobserved background exceptions.

The server owns each accepted background job until completion or shutdown. Cancelling a query or a request after successful admission does not cancel accepted work. Cancellation during admission reconciles any spawned process before releasing the single-run slot. Server shutdown stops admission and awaits bounded cleanup of its owned job. There is no public stop/interactive-input tool, persistence, automatic retry or concurrency increase. Cache retention is at most 20 IDs including the active ID; returned snapshots cannot mutate the cache and active results cannot be evicted. Restart invalidates all IDs.

Admission is the no-await sequence after successful spawn that registers the result ID and transfers the process to a retained server-owned background task. Before this point, cancellation or shutdown reconciles and reaps any spawning child. After it, request cancellation cannot revoke the accepted job. Shutdown closes admission first, observes both in-flight admissions and accepted workers, and awaits their bounded cleanup through the SDK lifespan. The ID is retrievable before the start response is exposed. Admission has its own completion future, resolved after child reconciliation and cwd-fd cleanup; shutdown does not wait for the caller's unrelated cancellation handling after this ownership interval.

Output-drain/process-wait cleanup has a separate one-second deadline and is protected from repeated cancellation. If an escaped descendant holds the output pipe open, the subprocess transport is closed and the direct child is reaped before releasing the slot. Deliberately escaped descendants remain the operator's responsibility; process-group cleanup is not OS resource isolation.

Task start returns immediately and results are polled because a Tunnel request has a finite response window; deadlines are not extended to cover long work, and a lost start response does not authorize a blind retry.

## Optional native CLI jobs

Operators may register Codex, Claude Code or OMP review and isolated candidate-edit jobs through `cli-job --config /absolute/private/config.json`, without changing the seven-tool MCP API. Operators register backend-specific exact task argv; remote callers write only `{target, mode, instruction}` to a request file in the configured workspace. Target aliases, source roots, file/edit allowlists, native runtime/auth paths and CLI controls remain outside remotely writable storage. There is no source auto-apply, test execution, commit/push, arbitrary shell, model override or adapter-level job retry. Jobs are disabled unless explicitly registered.

The parent verifies private configuration and runtime separation, pins regular UTF-8 source files, and snapshots only the selected allowlist. It rejects symlinks/hardlinks, hidden/protected paths, unexpected candidate entries, protected edits, and original-content/inode or source-root replacement conflicts. Native success means a completed provider stream, not a solved issue. Reports carry independent original/candidate and protected-file hashes, `verification: not_run`, and bounded SHA-256-addressed diff chunks under `cli-results/<backend>/<job_id>/`; the small stdout result identifies the complete report. Publication is staged and source originals are never written.

`cli_backend.py` requires external bubblewrap on non-root Linux, with mount/PID isolation, dropped capabilities, readonly runtime/system mounts and an allowlisted candidate at `/workspace`. Review has no writable source file; OMP/Codex edit overlays only approved existing files. A private tmpfs HOME `/home/job` separates native cache/helper state from the host home. Native capture allocations are bounded to 1 MiB and execution to 200 seconds, with bounded owned-group/pipe cleanup and namespace parent-death linkage.

**OMP.** Print mode emits JSON events whose tool results and transcript snapshots can exceed the capture budget even when the final answer is small. Events are consumed incrementally; every complete frame is validated and only the latest authoritative completion state and bounded final text are retained. A new `agent_start` or `turn_start` invalidates the prior completion candidate: EOF after a new unfinished lifecycle cannot reuse an old success. Success requires the current lifecycle's valid terminal snapshot, explicit final `stopReason: stop`, a bounded nonempty summary and normal exit zero. Recovered earlier attempt errors remain valid when a later lifecycle completes successfully. Malformed JSON/UTF-8, duplicate keys, nonfinite numbers, invalid completion, oversized individual frames/final summaries and incomplete trailing frames fail closed; a syntactically complete last JSON frame without a final LF remains valid. The guarantee is cumulative-stream tolerance, not unlimited individual records: every frame must stay within 980,992 bytes (958 KiB), with 2 KiB reserved for the retained final summary and 64 KiB for stderr, together within the 1 MiB budget. These are logical capture budgets, not an entire-process RSS guarantee. Ambient extensions/skills/rules/sessions/LSP/PTY and unrestricted tools are disabled.

**Codex.** Uses the native experimental app-server stdio protocol, fresh ephemeral threads, Code Mode and parent-owned dynamic file callbacks; stock exec/Code Mode has no builtin text-file API. `cli_file_tools.py` reuses the fd-safe `WorkspaceFiles` read and mandatory hash-guarded existing-file replacement, restricted to exact approved candidate paths. `cli_codex.py` verifies effective disabled tool categories before its single model turn and binds every callback/completion to the owned thread/turn. Unknown server requests, permissions/approvals, malformed frames, missing completion and oversized output fail closed. Fixed native configuration disables web search; readonly auth alone is mounted, not user Codex config/MCP servers/skills. Incompatible installed capabilities are rejected rather than silently falling back to exec or shell.

**Claude Code.** Uses a native executable plus an operator-private long-lived subscription token file (`claude setup-token`), without host `.claude.json`, `.credentials.json` or ambient settings/hooks/skills/plugins/MCP/session/browser mounts. The parent validates the token file (uid-owned regular, no group/other bits, single link, one value <=4 KiB) and passes it only as `CLAUDE_CODE_OAUTH_TOKEN` in bubblewrap's owner-only process environment: never argv (world-readable cmdline) and never a sandbox mount. Claude jobs therefore skip `--clearenv`; the environment is fully specified and every other name is overridden by `--setenv`. The operator-only `claude-token` command runs `claude setup-token` on a pseudo-terminal, mirrors it, saves the single detected token to a new 0600 file (atomic `--replace` for rotation) and falls back to hidden paste; it is never an MCP tool. Fixed safe-mode/restricted flags expose only Read for review and Read/Edit/Write for edit, without bare mode or permission bypass. For edit mode, minimal editable parent directories in the isolated candidate are writable for atomic replacement; noneditable files and subtrees without editable descendants are overmounted read-only. Temporary new entries are possible there; the candidate scanner rejects surviving extras, deletions or protected changes before publication. `cli_claude.py` validates the strict stream-json contract: one final result, integer exit 0, success subtype with `is_error: false`, completed reason, null API error, no permission denials or queued/additional results, and a bounded nonempty summary. A result with subtype success and `is_error: true` never publishes a passing candidate.

Failed jobs report `error_code: NATIVE_FAILED` plus only allowlisted diagnostics: the backend's fixed `native_error_code`, a fixed `native_detail` cause, an integer `native_exit_code` and a finite `native_elapsed_seconds`. Claude failures are classified from the terminal result frame before the exit-status check: 401/403 `AUTH_FAILED`, 429 `RATE_LIMITED`, other statuses `PROVIDER_ERROR`. Values outside the vocabulary are dropped; native text never crosses the boundary.

Native auth/config references are same-UID readonly paths, not copied or altered. They are readable by the native process, and networking is shared for providers: this is not a credential-secrecy or egress boundary. Allowed instruction/source/model output can contain secrets; no heuristic redaction is represented as protection.

## Operator commands

`dotunnel` is a separate operator command, never an MCP tool and never run implicitly by the server: `help`, `setup`, `update` and `doctor`. Bare `dotunnel` prints a pointer to `dotunnel help` and exits 2.

**setup** guides a self-hosting operator through the official Platform Tunnel/key URLs, organization/workspace association and runtime permissions. No browser login, API key/Tunnel creation, client download, account or service modification is automated. The target directory must be new with trusted root/operator-owned, rename-protected ancestors; ancestor symlinks and untrusted/non-sticky-writable parents are refused before credential input. Directories are 0700, key/config/profile files 0600. A tasks-disabled writable workspace is separate from credentials and runtime configuration. Credential input is terminal-only hidden prompt that aborts on echo fallback; there is no key CLI option or literal profile value. The official client configuration doctor is distinct from authentication. Optional foreground startup uses only the setup-owned process group and minimal environment; readiness requires live/ready health plus a successful control-plane poll. Failure/cancellation stops that client, preserves private files without overwriting them, and never claims access revocation or automatic restart.

After doctor, setup always checks Bubblewrap, required only for optional CLI integrations. `ready` needs a trusted `/usr/bin/bwrap` and a successful short probe with the job namespace flags (`--die-with-parent --unshare-all --cap-drop ALL`), so presence alone is not readiness. When it is missing and sudo appears available (non-interactive permission listing with `sudo -n -l` succeeds, or membership in `sudo`/`wheel`/`admin`), setup asks `[Y/n]` (Enter approves) and runs the distribution's non-interactive install argv on the same terminal, so sudo can prompt for its own password, then re-probes. This availability signal does not guarantee installation permission. Without sudo, after a declined or failed install, or for unknown distributions, it prints the command for an administrator. An unusable bwrap is never reinstalled; it reports namespace policy. This is the only OS change dotunnel can make, and only with that explicit approval. If CLIs are installed and Bubblewrap is still not ready, setup waits before any CLI prompt: Enter re-checks (continuing to selection in the same run once ready), `s` skips without touching the registry. A sudo-capable runtime account lets tasks and CLI jobs reach root, so documentation recommends installing from an administrator account and keeping the runtime account without sudo.

Administrative execution uses validated absolute system paths for sudo and the package manager, never inherited PATH lookups. New and existing setup require a terminal; the install consent boundary also fails closed without one. Existing profiles are not automatically changed during updates or integration reconfiguration.

Once Bubblewrap is ready, setup discovers installed Codex/Claude Code/OMP launchers without executing them. Up/Down moves, Space toggles, Enter applies and Esc/Ctrl-C cancels with exit 130 before any client start. Applying a selection validates every chosen source/edit scope and credential-reference metadata, writes private job configs and then replaces the task registry atomically. Unrelated tasks and the existing key/profile are preserved; deselecting removes only managed tasks. Credential contents are never read and no model request is made.

**doctor** is read-only and validates an existing setup. It starts no client and makes no model request. Readiness is reported only when observed from the local health endpoint, separately from config validity. The client is taken from PATH or an explicit absolute path, never from the current directory. It reports the same Bubblewrap status as setup and fails only when CLI integrations are configured and Bubblewrap is not ready.

**update** looks up the latest stable release from the fixed public GitHub Releases repository over anonymous standard-library HTTPS, without `gh` or login. An equal or newer installed version exits 0 without prompting. A newer release asks `Update now? [Y/n]` (Enter approves). EOF or a non-terminal fails closed, Ctrl-C exits 130. Installation is limited to a non-root Linux, non-editable virtualenv installation. The release wheel must have the exact name for its tag, and its size, GitHub-reported SHA-256 and package Name/Version are verified before a binary-only uv or pip installation into the current interpreter's prefix. Metadata (1 MiB), download (16 MiB), network waits and installer execution are bounded. It never changes configuration, credentials or services and does not restart running processes.

## Installation and account policy

Documentation offers two Linux execution modes: a dedicated non-admin account (recommended) or an explicitly chosen existing non-root account. Nothing here modifies existing users, groups or paths automatically, overwrites an existing account, or recursively changes ownership of shared projects. The only package change dotunnel can make is the explicitly approved Bubblewrap installation described above; other administrative commands are instructions only.

Separate, non-overlapping locations are required for the installed program, trusted configuration/credentials and the writable workspace.

## Verification

Tests use stdlib unittest for boundary behavior: path and symlink escapes, hash conflicts, task admission and cancellation races, protocol framing, configuration rejection and credential-reference handling. An SDK stdio subprocess smoke negotiates initialize, lists tools, reads/searches/creates/replaces fixture files, runs a fixed harmless task, fetches exact results and exercises unauthorized paths and tasks. Use only synthetic fixtures. Native CLI behavior is covered with local fake executables and protocol fixtures; a model-provider call is a separate explicit operator check.
